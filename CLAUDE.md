# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Obsidian plugin (`obsidian-map-manager`) that lets users design interactive square/hexagonal grid maps with a background image, zone coloring, stamps, tokens, and note links, either in a dedicated file view or embedded in a note via a `map` code block. Map data is stored as JSON in `.map` files inside the vault (a custom file extension registered by the plugin). UI strings in the source are in French (this is the plugin's actual UI language, not a placeholder).

## Commands

- `npm run dev` — compile `src/main.ts` → `main.js` **and** `src/view/customScript.ts` → `map-manager-viewer.js`, both in watch mode (esbuild).
- `npm run build` — type-check (`tsc -noEmit -skipLibCheck`) then produce minified production `main.js` and `map-manager-viewer.js`.
- `npm run lint` — run ESLint (`eslint-plugin-obsidianmd` recommended rules + typescript-eslint + a `no-restricted-imports` rule forbidding `obsidian` in the public-viewer file set, see below).
- There is no test suite in this repo.
- To try changes in Obsidian: this plugin's repo lives directly inside a vault's `.obsidian/plugins/obsidian-map-manager` folder, so `npm run dev` + reloading Obsidian (or disabling/re-enabling the plugin) is the whole dev loop. `main.js` and `map-manager-viewer.js` are gitignored — built locally, not committed, and sit side by side in the plugin's own folder (`<vault>/.obsidian/plugins/obsidian-map-manager/`). `map-manager-viewer.js` isn't loaded by Obsidian itself — the "Installer/mettre à jour le script de vue publique" command copies it from there into a normal vault file (see below).

## Architecture

**Data flow:** `MapFileData` (in [src/data/mapData.ts](src/data/mapData.ts)) is the single serialized JSON shape for a `.map` file. `parseMapData`/`serializeMapData` are the only read/write boundary — all migration logic for old file versions lives in `normalizeMapData` (see "Versioning" below). Everything else — controller, canvas, UI panels — operates on the in-memory `MapFileData` object, never on raw JSON.

**MapController** ([src/controller/MapController.ts](src/controller/MapController.ts)) owns one open map's `MapFileData` plus UI-only session state (selection, active tool, brush settings, undo/redo stack). It's the sole mutation point: all edits go through `update()`, which snapshots history, runs the mutator, notifies listeners, and triggers save. Both the full-tab view and embedded-in-note view construct their own `MapController` instance around the same data shape — there's no shared/global state between multiple open instances of the same map.

**Two hosts, one component tree:** [src/view/MapView.ts](src/view/MapView.ts) (a `TextFileView` for `.map` files opened as a tab, mode `"edit"`) and [src/view/MapEmbed.ts](src/view/MapEmbed.ts) (a markdown code-block processor for `` ```map `` blocks, mode `"view"`, read/written via `app.vault.process` with a debounced save) both wire up the same four UI components against a `MapController`: `Toolbar`, `LayersPanel`, `MapCanvas`, `InfoPanel`. When changing how these fit together, keep both call sites in sync.

**MapCanvas** ([src/render/MapCanvas.ts](src/render/MapCanvas.ts), ~1200 lines) is a hand-rolled `<canvas>` 2D renderer and input handler — no framework, no virtual DOM. It owns pan/zoom (`ViewTransform`), hit-testing, drag state for tokens/markers, brush/fill painting, and fog-of-war (line-of-sight + vision cones). Grid math (coordinate conversions, hex/square cell lookup, visible-cell culling) is factored out into [src/grid/gridMath.ts](src/grid/gridMath.ts) and is pure/stateless — prefer adding new coordinate math there rather than inline in the canvas.

**Grid types:** `"square"`, `"hex-pointy"`, `"hex-flat"`, `"none"` (freeform, no cells — tokens/markers get free `x,y` world coordinates instead of a `cellKey`). Most cell-keyed data (`CellData`) is stored per-grid-type in `cellsByGridType` so switching grid types on a map doesn't lose data from the other type. Tokens are map-level (not per-layer or per-grid-type) so they persist across layer/grid-type switches; their `cellKey` is just reinterpreted under whichever grid is currently active.

**Layers:** each `Layer` has its own background image, `cellsByGridType`, and freeform `markers`; tokens are layer-independent (see above). Only one layer is "active" (edited) at a time via `activeLayerId`.

**Fog of war** (view mode only): two rendering paths, split by grid type.
- **Celled grids** (`square`/`hex-*`) use the "avec grillage" fog — `FogRenderer.renderCellFog` + the pure geometry helpers in [src/grid/fog.ts](src/grid/fog.ts) (`cellPolygon`, `isCellFullyLit`, `concaveCornerBlackTriangles`, `cellsWallSeparated`, `exploredCellsInRect`). Each cell is fully black ("fog") or half-opacity ("explored", i.e. `key ∈ exploredCellsByGridType[gridType]`); a player token sees exactly "line of sight ∩ light". Each lit shape is handled in two steps: first the real fog is cleared fully away (`destination-out`, **solid** — the light wins over the fog right out to its rim) straight on the fog buffer, then a purely cosmetic radial vignette is accumulated on a dedicated `FogRenderer.vignetteCanvas` (fill every lit shape with the fog's own `rgba(8,8,12)` tint — stroked `LIGHT_EDGE_SEAL_PX` past each edge so the tint covers the anti-aliased seam left by the solid clear, otherwise a faint 1px ring shows at the rim — then `destination-out` each light's `FogRenderer.lightClearnessGradient`: full erase through the inner clear-core plateau, then a **linear** ramp down to 0 erase at the rim) and blitted back over the cleared ground in one pass. Accumulating on its own buffer is the point: every light erases the *same* pre-filled tint, so two overlapping lights only ever brighten their overlap, never stack their dark tint. The **only** animated part of a light is `FogRenderer.lightCoreRatio` — the clear-core plateau breathes between `0` and `LIGHT_CLEAR_CORE_RATIO` (20% of the reach) on a gentle two-sine guttering, each source with its own phase *and* rate (a well-mixed `tremblePhase` seed) so they drift apart rather than pulsing in lockstep; the reach, the falloff shape and the fog-clearing circle never move. Driven by the same `syncAnimationLoop` RAF whenever `lightFlickerActive` (a light in view, zoom not out past `FOG_ANIMATION_MIN_ZOOM`), regardless of "Adoucir le brouillard". None of this shading gates exploration or entity visibility, which use exact steady geometry. The token's own light circle is `fog.ts`'s `traceVisibilityPolygon` traced to exactly its `lightRadius`, then `FogRenderer.lightCirclePath` redraws every unobstructed span of that polygon as the true circle arc — so the lit edge is a perfect circle around the token, straight only where a wall actually cuts it (no `VIS_MAX_STEP` fan of facets against the explored/fog frontier). Separately, every other light source's wall-clipped reach (`frameLightRawCache`) is punched clipped to the token's *full* line-of-sight polygon (`traceVisibilityPolygon` traced well past the screen: rays at every wall corner ±ε so a shadow edge is one straight line past the corner), so another lit room shows only where this player's line of sight actually reaches it; a cell a player can wholly see right now (`isCellFullyLit` — every sample point inside some light circle it has line of sight to, and in a player token's line of sight; so a room lit by an outside torch the player can see also unlocks) becomes permanently explored via `MapController.markExplored` unless `fogFrozen`; a concave corner of an explored cell (two orthogonal fog neighbours, wall-separated ones excluded) is cut on the diagonal (square grids only). `exploredCellsByGridType` is per grid type like `Layer.cellsByGridType` — switching grid type starts that type's fog fresh.
- **Grid type `"none"`** keeps the legacy ray-traced/coarse-bucket fog (`FogRenderer.drawFog`/`renderAndComposite`/`drawWallShadowBlackout`), whose memory is the grid-independent world-bucket set `exploredCells`. Fog runs on a hidden `square` cell substrate there — see the comment on `MapController.updateCell`.
- **"Adoucir le brouillard"** (`settings.fogSoftening`, a 0-10 intensity slider, default 3) replaces the old 3-way `fogAnimationMode`, then the on/off boolean: at `0` the fog edge itself is crisp and static (the light-source flicker still runs its own redraw loop if a light is in view — see above); `1-10` draws a fade on the explored side of the explored/fog frontier (celled grids) / the legacy edge tremble (grid `"none"`), with a `requestAnimationFrame` loop while active (`FogRenderer.syncAnimationLoop`, shared with the flicker). The celled-grid fade is `drawFogSofteningRamp` in [src/render/drawing.ts](src/render/drawing.ts) (shared by `FogRenderer.renderCellFog` and the export's `drawCellFogMask`): on an offscreen scratch it fills the fog region solid at `edgeAlpha` and, for every explored cell that borders fog, adds a linear gradient per fog-bordering edge running one cell width into that cell (`edgeAlpha` flush against the fog edge → fully transparent at the cell's far side; a corner cell darkens in both directions), then lightly blurs the scratch (just enough to connect neighbouring cells' gradients across shared corners so a diagonal frontier isn't stair-stepped — `fogSofteningParams.blurRatio`) and composites it back once. The slider (`fogSofteningParams`) scales only `edgeAlpha` — how black the gradient starts against the fog — never how far it reaches; the band is always the one bordering cell. At `10` the fog edge is full black.

**Gamepad control** (the poller is never created for a mirror canvas — it lives on the GM's source canvas): [src/controller/gamepadInput.ts](src/controller/gamepadInput.ts)'s `GamepadInputPoller` turns a connected pad into callbacks wired in `MapCanvas`'s constructor against the player token assigned to that pad (`MapController.gamepadAssignments`, session-only, set from `InfoPanel`'s "Manette" field). It only actually drives tokens when `MapCanvas.gamepadControlAllowed()` — the shared `mode` is `"view"`, **or** a player-mirror window is open (`MapController.hasPlayerMirror`, ref-counted by `MapPlayerMirrorView` mount/unmount), so the GM can flip their own window to Édition to tweak the map while players keep moving on the second screen. Left stick / d-pad steps the token cell-to-cell (`handleGamepadMove` → `MapController.moveToken` + a "jump" hop animation echoed to any mirror); R1 refills (`LIGHT_REFILL_PERCENT`, +50) / L1 dims (`LIGHT_DIM_PERCENT`, −10 per press, edge-triggered) or, held ≥ `LIGHT_EXTINGUISH_HOLD_MS` (1.5 s), snuffs to 0 — acting on the co-located "light" fixture's `lightLife` if there is one, else the player's own; right stick is a live "look" override committed to `rotation` on release. Every token's light life is also shown (and nudgeable) in the GM's "Vue"-mode InfoPanel, all categories (`InfoPanel.renderTokenLightLifeField`) — never on the player-facing mirror panel. **Triangle/Y opens the action menu**: `handleGamepadActionButton` resolves `settings.gamepadActions` against the token's current contact (`resolveAvailableActions` — `none` / any *franchissable* wall segment (`pass-through`/`pass-see-through`, no sub-type choice) on a neighbour edge / a `light`/`player`/`entity` token on the same or an adjacent cell), then 0 available → nothing, 1 → run it, ≥2 → open a popup menu (`MapController.gamepadActionMenus`, session-only + `notify()`-driven so the mirror draws the same menu via `MapCanvas.syncActionMenuOverlay`, a DOM overlay anchored just above the driving token). D-pad **up/down only** moves the menu cursor (left/right ignored; each move drains `settings.actionMenuNavCost` from `lightLife`), Croix/A confirms, Rond/B cancels — and Rond/B with no menu open instead dismisses a still-showing "ouvrir une note" sidebar. An action's effect (`executeActionOption`) is "passer outre" (step across the contacted wall), "changer le type du mur" (`setWallSegmentBlockerType`), "allumer/éteindre la lumière du token" (only offered with a `token:light` contact, and only for a light whose `Token.lightInteractable` isn't `false` — same gate excludes a locked light from `MapCanvas.colocatedLight`, so L1/R1 skip it too — toggles *that contacted "light" token's* own `lightLife` 100 ⇄ 0, not the player's), or "ouvrir une note" (opens `MapController.gamepadActionNotes[gamepadIndex]` — session-only + `notify()`-driven like `gamepadActionMenus`, so both the GM canvas and any mirror render the same note off shared state, no echo channel; `MapCanvas.syncActionNoteOverlay` renders each open note via `renderLinkedNote` — a linked vault note / heading section, same resolution as `InfoPanel.renderLinkContent` — as a **full-height sidebar docked on the left/right map edge by player number** (`MapCanvas.playerSlotRect`, players = connected gamepads sorted by index: odd players dock left, even right, each edge splitting its height evenly among its players top-to-bottom — 1 player fills the left edge, 2 take a full edge each, 3 split the left edge 50/50 (p1/p3) with p2 owning the right edge, and so on), closed with Rond/B) — the two wall effects roll the wall's `triggerWallClock`; all then drain the action's `lightCost` plus the usual `drainLightForEvent("action")`. The live "!" indicator over an assigned token (`tokenCanInteract`) only lights for *contact-based* actions, never a `contact: "none"` one. Walls no longer have a hold-to-pass shortcut — every crossing goes through a `"pass-through"` action now.

**Versioning:** `MapFileData.version` is bumped whenever the stored shape changes; `normalizeMapData` in [src/data/mapData.ts](src/data/mapData.ts) contains the full migration chain (pixel-vs-cell background offsets pre-v3, per-layer vs. map-level tokens pre-v5/v6, boolean vs. string vision blockers pre-v10, zone types/token templates moved out of `MapFileData` entirely pre-v13, a player token's vision cone facing folded from its own `visionDirection` into the token's general-purpose `rotation` pre-v14, `VisionBlockerType`'s 2-value `"opaque" | "dim"` expanded to today's 4-value vision/movement matrix pre-v15 (old `"dim"` folds onto `"see-through"` — see its own doc comment), a token light's boolean `lightEnabled` on/off flag replaced pre-v17 by a `lightLife` percentage (0-100, which also scales the lit fraction of `lightRadius`) plus per-move/per-action drain settings — an old `lightEnabled: false` folds onto `lightRadius: 0` (see `parseToken`), celled-grid fog memory moved pre-v18 from the coarse world-bucket `exploredCells` to per-grid-type cell keys `exploredCellsByGridType` (a coordinate-system change, so pre-v18 celled-grid memory is dropped — same call as the v11 bucket switch; `exploredCells` is kept as the grid-`"none"` memory store), a `"light"` token's optional `lightInteractable` boolean added v19 (purely additive — unset reads as "yes"; gates whether players may tend the fixture via the gamepad — see below), etc.). When changing `MapFileData`, bump `version` and add a migration branch rather than assuming old files match the new shape.

**Settings** ([src/settings/types.ts](src/settings/types.ts)) hold the *defaults* applied to newly-created maps (grid type, cell size, zoom range) plus the assets folder, embed height, the global `fogSoftening` 0-10 slider ("Adoucir le brouillard" — see "Fog of war" above; also frozen into `PublicMapSnapshot.fogSoftening` at publish time), the `fogDebugVisionRays` debug overlay toggle (`FogRenderer.drawDebugVisionRays`), and the `gamepadActions` list + `actionMenuNavCost` for the gamepad action menu (see "Gamepad control" above) — they don't affect existing `.map` files after creation. **Exception:** `defaultZoneTypes`/`defaultTokenTemplates` (and, like them, `gamepadActions`) are not per-map at all — `ZoneType`/`TokenTemplate` were removed from `MapFileData` in v13 (they used to be copied into each map at creation time, which meant editing Settings afterward silently had no effect on already-open maps). `Toolbar`/`InfoPanel`/`MapCanvas` now read `settings.defaultZoneTypes`/`defaultTokenTemplates` live instead of `data.zoneTypes`/`data.tokenTemplates`; `MapManagerPlugin.onSettingsChanged`/`MapController.refresh` push an immediate re-render to any already-open map when Settings are edited, so there's exactly one global list, always in sync everywhere. The public export (below) is the one place that still needs its own frozen copy, since the exported site has no live Settings to read from.

**Public viewer (read-only, external site):** the in-Obsidian View mode (`MapCanvas`/`Toolbar`/`InfoPanel` with `controller.mode === "view"`) lets a GM move tokens and toggle fog live — that stays Obsidian-only. For publishing a frozen, read-only snapshot to an external static site (built by a separate site-export plugin — this repo only produces artifacts for it to consume, it doesn't manage distribution/installation itself), two independent, loosely-coupled artifacts get produced:

1. **Per-map data** — "Publier la vue" (View-mode toolbar button, or the "Publier la vue publique de la carte active" command) runs `buildPublicSnapshot` ([src/data/mapRedaction.ts](src/data/mapRedaction.ts)) to strip everything hidden by fog (unexplored cells — celled grids test `key ∈ exploredCellsByGridType[gridType]`, grid `"none"` the coarse `exploredCells` buckets — out-of-vision markers/entity tokens, all wall geometry, and non-active grid types' explored memory — never just visually hidden, actually absent from the output), then `rewriteAssetPathsForSite` ([src/data/publicAssetPaths.ts](src/data/publicAssetPaths.ts)) to turn background/token image paths into site-root-absolute references (the site-export plugin copies vault attachments under the Svelte project's `static/` folder, which SvelteKit serves at the site root), then `renderNoteSnapshot` ([src/platform/renderNoteSnapshot.ts](src/platform/renderNoteSnapshot.ts)) to bake linked notes into sanitized, link-neutralized static HTML and resolve token stat-blocks (both need vault/`MarkdownRenderer` access, hence Obsidian-only), plus a frozen-at-publish-time copy of live `settings.defaultZoneTypes` (into `PublicMapSnapshot.zoneTypes`, since zone types aren't part of `MapFileData` — see "Settings" above; `defaultTokenTemplates` needs no equivalent field, since the resolved stat values are already baked into `tokenStats`) and of `settings.fogSoftening` (into `PublicMapSnapshot.fogSoftening`). `publishPublicSnapshot` ([src/platform/publishPublicSnapshot.ts](src/platform/publishPublicSnapshot.ts)) writes the result as `<basename>.json` next to the `.map` file (`publicSnapshotPath` in [src/data/mapData.ts](src/data/mapData.ts)) — a plain vault file like any other, picked up by whatever the site-export plugin already does to mirror vault files onto the site.
2. **One shared renderer script** — `src/view/customScript.ts` bundles the whole read-only renderer (`PublicMapCanvas`, `PublicInfoPanel`, `mountPublicMapViewer`) into a single self-contained file with a default-exported bootstrap function (`export default function`, no arguments), matching the site-export plugin's generic "custom scripts" convention (any script registered there gets called client-side after the page mounts) without that plugin needing any Map Manager-specific code. `npm run build` is this plugin's *only* responsibility here — getting `map-manager-viewer.js` into the site is entirely up to whoever wires up that "custom scripts" registration; nothing in this repo copies, installs, or configures it. The bootstrap scans the page for `` ```map ``` `` code blocks passed through as `<code class="language-map">` by the site's markdown pipeline and `fetch()`es the matching `<basename>.json` (`resolveDataUrl` in `customScript.ts`): a `./`- or `../`-prefixed map path resolves against the *current note's own folder* (`currentPageFolderUrl` — normalizes away trailing-slash routing differences; relies on the site mirroring the vault's folder structure, so "the note's folder" and "the page's folder" are the same thing); anything else is treated as vault-root-relative, prefixed with the optional `window.MAP_MANAGER_VIEWER_BASE_URL` (defaults to `"/"`) — matching how the in-Obsidian embed resolves a non-bracketed path. There's no toolbar (per "impossible de jouer depuis le site" — pan/zoom are built into the canvas itself, no +/−/recenter buttons); `mountPublicMapViewer` injects a small self-contained default stylesheet ([src/view/publicViewerStyles.ts](src/view/publicViewerStyles.ts), styled with real Obsidian CSS variables like `--background-primary`/`--text-normal`, hardcoded light-theme values only as fallbacks) once per page so the info panel docks on the right like it does in Obsidian, instead of stacking unstyled. Those variables are always defined inside Obsidian; the site-export plugin's own `app.css` mirrors the same variable names for the exported site, so this needs no plugin-specific CSS on that end.

Everything `src/view/customScript.ts` pulls in (`PublicMapCanvas`, `PublicInfoPanel`, `PublicViewController`, `mountPublicMapViewer`, plus `src/grid/**`, `src/data/**`, `src/controller/**`, `src/render/drawing.ts`) has **zero `obsidian` import**, enforced by an ESLint `no-restricted-imports` override in [eslint.config.mts](eslint.config.mts) scoped to exactly that file set — `npm run build` bundles it standalone into `map-manager-viewer.js` (esbuild, ESM, no externals, no separate type declarations needed since it's consumed at runtime, not imported by a TS build). When adding to the public viewer, keep new code within that pure file set, or the lint rule (and the standalone bundle) will break.

## Conventions

- Tabs for indentation, LF line endings, UTF-8 (see [.editorconfig](.editorconfig)).
- `noUncheckedIndexedAccess` and `strictNullChecks` are on — index access into records/arrays returns possibly-`undefined`; handle it rather than asserting.
- `main.js` is a generated bundle (esbuild banner points back to source) — never hand-edit it; edit `src/` and rebuild.
- ESLint config extends `eslint-plugin-obsidianmd`'s recommended rules — follow Obsidian-specific API guidance it enforces (e.g. around `normalizePath`, detached DOM, etc.).
